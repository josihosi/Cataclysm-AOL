# FS migration approval review

Decision: **do not approve for activation yet**.

The repaired candidate has a material reopen projection bug in the new FS-only delivery path. In `/tmp/de67-fs-migration-candidate.DtTbAZ/scripts/deadline_harness.py:91-94`, `_open_ledger_baseline()` uses raw regexes containing `\\n?` and `\\A` (two backslashes). They therefore search for a literal backslash sequence rather than a newline/start anchor. When an accepted claim is invalidated, `synchronize_delivery_statuses()` calls this helper at lines 1757-1760, but the checked ledger claim and its `Durable acceptance` line remain unchanged. A closure reopen can consequently leave the claim checked, and the ledger projection no longer reflects the authoritative invalidation/reopen state. This is candidate-introduced behavior (the helper and FS projection are added in the original migration candidate); it is directly on the requested ledger acceptance/reopen lifecycle and blocks honest activation.

The same new query at lines 1729-1740 computes `MAX(acceptance_number)` across all lineages before filtering `accepted.lineage_id` in the outer query. If another lineage has a higher acceptance number for the same claim, the current lineage's latest acceptance is omitted from projection. This is an additional isolation gap in the FS path; the legacy path has the analogous pre-existing query, so it should be fixed in the migration path or explicitly carried as inherited risk before approval.

Verification: the candidate's migration-specific specification tests pass under `python3 -m unittest` (the full candidate suite ran 448 tests, 5 failures, 19 errors, 4 skips, matching the coordinator's reported candidate totals). The changed-count comparison does not clear the reopen defect: a direct call to `_open_ledger_baseline()` on a checked block with a durable-acceptance line returned the block unchanged. The reported baseline was 445 tests, 5 failures, 20 errors; most remaining failures/errors are inherited fixture/environment failures, but the reopen defect is a new correctness issue independent of those counts.

Required before approval: correct the regexes to actual newline/start-anchor expressions, add a regression test that invalidates an accepted FS claim and verifies the ledger reopens/removes the durable projection, and scope latest-acceptance selection by `lineage_id` in the FS query (with a cross-lineage test).
