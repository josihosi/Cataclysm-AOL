# Returned worker lifecycle scope

## Findings

### Worker return and continuation

- `worker_library.py::_idle` treats an assignment as reusable only when its deadline task has `attempt_terminal_at`, or when a rejected request no longer owns the task. A normal worker return is recorded by `WorkerDispatcher.observe` as assignment status `returned`, but it leaves the task open and the claim unreleased. Therefore `_idle(returned)` is false.
- `worker_library.py::message` accepts statuses `running`, `returned`, `failed`, and `interrupted`, but also rejects when `_idle(assignment)` is true/false in the same predicate. The current returned/open case is rejected before the continuation request is queued. This is the direct coupling that strands unfinished returned work.
- `worker_library.py::process_pending` already has the intended continuation route: a `message` request for a non-running assignment resumes the stored worker thread, then starts a new turn; it does not call `claim_worker` or create a new assignment. `WorkerDispatcher.observe` records the new turn as another result and `worker-return` checkpoint. The smallest continuation repair is to separate “reusable for a new assignment” from “continuable existing assignment”, and let a returned/failed/interrupted assignment continue when its prior worker server is inactive and its durable worker/claim credentials still match. Preserve the existing assignment id, task id, worker id, claim id, coordinator owner credential, supervisor id, checkpoints, receipts, and deadline history.
- Fresh coordinator review continuation currently has a second coupling: `worker_library.py::message` requires the assignment binding thread id to equal the current coordinator thread id, and its ownership check compares `tasks.coordinator_session_id` to the current binding thread id. After a fresh coordinator, the task still correctly records the prior Sol owner. Continuation must authenticate against the assignment’s preserved owner binding (worker id + prior coordinator session + claim supervisor), while recording the current coordinator binding for the new request; it must not transfer the task or create a new claim. Keep the old server-presence check so a live prior App Server cannot be adopted ambiguously.
- `worker_library.py::WorkerDispatcher._reconcile_one` and `process_pending` already provide inactive-thread checks (`thread/read`, `thread/resume`, active-thread rejection) and stale request protection. Reuse those checks; do not add a new lifecycle state or a second worker registry.
- `worker_library.py::retire` must continue to mean “retire a reusable worker”; a returned/open assignment is not idle for retirement, because it remains continuable. The returned worker should become retireable only after the existing task/claim settlement path makes it truly idle.

### Review gate and deadline clocks

- `coordinator_supervisor.py::mutation_gate` calls `DeadlineHarness.list_tasks()` and returns no gate whenever any projected task has `state == "running"`. The projection is task/clock state, not worker App Server liveness or returned assignment status. An open task whose worker turn has returned is therefore indistinguishable from active execution at this gate.
- `policy_kernel.py::workspace_facts` independently adds `live_task` for every nonterminal task with an unreleased `worker_claims` row. It likewise has no returned/inactive distinction. This fact is useful for normal coordination, but must not be a blanket mutation-review veto once the worker registry proves all relevant windows are returned/inactive.
- `deadline_harness.py::retire_claim_clocks_for_mutation` unconditionally queries every nonterminal task and raises `DeadlineError("Mutation cannot retire clocks while a worker attempt is running: ...")`. That phrase and query currently treat an open returned task as running. Retirement needs a narrow supplied/derived “actually running worker attempt” test, while preserving the open task, claim, miss records, checkpoints and all prior generations. A returned/open task must remain resumable after review under the same claim history.
- `coordinator_supervisor.py::_complete_mutation_review` calls clock retirement before launching the reviewer and then requires one fresh coordinator restart. This is the correct exclusive boundary once the gate’s quiescence predicate and the harness retirement predicate agree on actual execution liveness.
- `coordinator_supervisor.py::active_worker_coordinator_session` only considers unreleased claims with nonterminal tasks; it will return the old coordinator session for a genuinely active worker claim, but returns no session for a returned worker only if the claim was released/normalized. Do not use a blanket “live task row exists” test to choose review or successor ownership. For a returned/open claim that remains unreleased, preserve the durable old coordinator session as the task owner and use the worker-library assignment identity to authorize continuation.

## Smallest coherent implementation shape

1. Add/reuse a predicate in `worker_library.py` for “continuable existing assignment”: status is returned/failed/interrupted (or running for steering), worker id and task claim still match, task is nonterminal/unreleased, and the prior server is absent or the current binding is unchanged. Use this predicate in `message` and in the non-running `process_pending` branch. Keep `_idle` reserved for new-job reuse and retirement.
2. Permit the current coordinator to queue continuation against the assignment’s preserved task-owner credentials after review, without overwriting `tasks.coordinator_session_id` or `worker_claims.coordinator_session_id`; update only the assignment request binding as already designed. Reject a different worker, released/terminal claim, live prior server, ambiguous start, or stale workspace/lineage.
3. Make `coordinator_supervisor.py::mutation_gate` consult worker-library assignment/runtime evidence for actual execution liveness. A returned/inactive assignment may coexist with `live_task` and must not block the exclusive review. Keep a gate blocked for any actually running, submitting, uncertain, active App Server turn, or unresolved ownership ambiguity.
4. Make `deadline_harness.py::retire_claim_clocks_for_mutation` reject only those actually running/ambiguous worker attempts. Retire active clock generations while leaving nonterminal task rows and unreleased returned claims intact for post-review continuation; do not call `normalize_external_supervisor_start` and do not rewrite miss/history.
5. Keep `policy_kernel.py::workspace_facts`’s `live_task` meaning for ordinary routing, but adjust the mutation route’s obligations/decision input so `live_task` alone is not a review veto when worker lifecycle evidence says returned/inactive. Do not add a new fact framework or checkpoint-before-continuation gate.

## Acceptance boundary

Review is eligible when every worker window is actually returned/inactive or otherwise durably reconciled, even if an open task row and claim remain. Review retires the current clock generation without erasing the open claim’s miss/history. The same named worker resumes the unfinished assignment after the fresh coordinator using preserved worker/task/claim credentials, and later settlement alone closes the task. Any active or ambiguous worker execution still blocks review.
