# R-CAOL-BULK-ITEM-COST: disposable workload and measurement design

Status: preparation only. No game was launched, no GUI or broker input was taken, and no source or owner save was changed for this design. Native execution waits for explicit input handoff from `camp_runtime_recovery` through Sol.

## Preserve comparability

- Build a task-owned, native-created sandbox world from the current executable. Keep unrelated NPCs, monsters, vehicles, jobs and active items away from the workload area. Do not base the run on `.userdata/reference-saves`; those are preserved owner records. The existing `r009_m059_preopportunity_bootstrap` is also a poor isolated base: its manifest records 12 camp members, which can add unrelated turn work.
- Complete setup once, save and quit natively, then use independent disposable copies of that exact world for baseline and repaired runs. Record source revision/dirty state, executable hash, world/player save hashes, platform/renderer, seed, game turn, player position, local actor counts, source/destination positions and capacities. Confirm the copies match before the measured action.
- Ask the owner for the approximate item counts and zone/source layout from the severe manual case during handoff. Use those observed values as the primary workload; do not substitute an arbitrary pass threshold. If the owner cannot recover them, record the chosen measured counts explicitly and describe that run as representative rather than an exact reproduction.

## Workloads

1. **Advanced-inventory plank transfer.** Place a recorded number of player-owned `plank` items on one source tile, with an adjacent empty floor tile as the map destination. Use the advanced inventory menu's normal bulk action and wait for the native activity to finish. Record exact item count, charge count (if any), source/destination, destination capacity, pane sort order, and actor identity. Keep a small single-item transfer as a route/control check on its own copy. If the owner's actual transfer used inventory, vehicle cargo, multiple source tiles or another destination, reproduce that layout instead and report it as a distinct workload.
2. **Zone sorting of unsorted items.** Place the measured item population in one `LOOT_UNSORTED` tile and configure adjacent destination zones that accept every included type. Keep the population heterogeneous by using the observed item types; at minimum, include more than one destination class if the reported case did. Record type counts, charges, ownership, nested contents, source tiles, destination zone identities/types, destination capacities, vehicle state and actor count. First profile one source tile; add multiple sources only if the owner case or first profile shows that source discovery/routing is material.
3. **Control states.** Keep a separate capacity-full/blocked destination start for each affected path, so its behavior is not mixed into the primary timing. On a separate copy, interrupt after partial progress, save/reload through the native route, resume, and census items before and after the interruption. Do not count a canceled or partially completed operation as a completed throughput result.

## Measurement lanes

- **UI/collection:** time opening advanced inventory, building/rebuilding the two panes, changing sort order, selecting bulk transfer, and returning from the menu. The existing trace brackets `handle_action` and records an `input` phase; this phase includes both menu work and time waiting for the next key, so report it as end-to-end input/menu wall time, not pure UI compute. Record automation/key timestamps and stable post-action frame times to identify operator wait. `game::do_turn` reports `simulation_seconds` with explicit `input` and `save` time removed. Preserve the trace with exact run/process binding.
- **Native activity and zone routing:** record start/finish request boundaries, actual advanced game-turn delta, wall elapsed time, CPU seconds and RSS from the run-bound harness performance owner. The native activity-driver log brackets `handle_action` and pre/post-input `activity.do_turn` calls with activity type and moves; correlate those events with turn trace and action identities. Collect short `/usr/bin/sample PID duration interval` stack samples only from the task-owned game, in distinct intervals: menu open/rebuild, bulk activity, and zone-sort activity. Keep each sample file with its phase label and run/process identity. Use separate equivalent profiled and unprofiled copies so sampling overhead does not contaminate the timing comparison. The host has no `xctrace` utility available from its installed Command Line Tools; do not claim an Instruments trace.
- **Work completed:** record input item count, transferred item count, activity completion/interruption state, moves/turns consumed and zone source/destination counts. For zone sorting, retain activity debug messages for source scans, route attempts and pickup/drop batches. Use sampled stacks for cost attribution; wall time or CPU totals alone do not establish the expensive function.
- **Separate costs:** report menu/input wall and process CPU, native activity wall and CPU, and native simulation-only seconds/game turns as separate rows. Treat harness action latency as an end-to-end action interval, not as pure simulation time.

## Conservation census

At the saved starting checkpoint, after complete transfer/sorting, and at the interruption checkpoint, count physical item instances exactly once across ground map tiles, vehicle cargo, player inventory/worn/wielded storage, nested container contents and any activity-carried items. Activity targets are references, not a second copy of their items; `zone_sort_activity_actor::picked_up_stuff` must be included only through the carrier that physically owns the item. Compare a multiset keyed by type, charges/count, damage/active state, ownership and recursively serialized contents, plus location totals for the tested source, destinations, player and temporary carrier. For these non-container workload items, exact per-type counts and charge totals must match the expected source-to-destination movement. Preserve the raw native save and census output for each run.

## Existing mechanisms and gaps

- `advanced_inventory::recalc_pane` owns pane collection and stable sorting; `move_all_items`/`fill_lists_with_pane_items` construct bulk work; `move_items_activity_actor::do_turn` processes item locations and charges pickup move cost.
- `zone_sort_activity_actor::stage_think` collects items and checks destinations; `stage_do` processes source items and routing. Its serializer persists `picked_up_stuff`, so the interruption checkpoint can examine real resume state.
- Existing focused controls passed on the available test build: `[items][advanced_inv]` (1 case, 196 assertions) and `[zones][items][activities][sorting]` (39 cases, 252 assertions). They are baseline behavior evidence, not large-workload profiling or native conservation proof.
- No production counters are proposed yet. First profile the real operation with existing turn/performance telemetry and phase-bounded stack samples; add narrow counters only if the profile cannot distinguish the expensive owner.
