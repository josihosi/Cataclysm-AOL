# Bulk item performance findings (2026-09-24)

Native static-sort runs B0/B1/B2 all used the same 256-item workload (128 `2x4` + 128 hammers), same living-NPC La Mirada premise, and returned to World at turn 5212951 from 5212800 (+151 turns). Operation wall interval from first post-selection `turn/start` to the returned World surface was 0.687 s (B0), 0.927 s (B1), and 0.939 s (B2). B0/B1 were before the candidate edit; B2 used the rebuilt candidate binary. This is an end-to-end operation envelope, not actor-only CPU time. There is no measurable improvement in this three-run sample; B0 is faster, and observation scheduling/noise dominate the ~0.25 s spread. B2 has same game-turn count; it does not establish a post-fix result because native census contradicts conservation and the candidate edit was placed in `unload_loot_activity_actor`, not the static `zone_sort_activity_actor` path.

AIM native transfer A0/A1 each moved 241 items at the UI-reported destination limit and advanced +123/+122 turns. First post-action turn to returned World was 137.579 s (A0) and 16.221 s (A1); those intervals include large unobserved UI/activity waits and are not comparable operation timings. A0's ACT_MOVE_ITEMS-labeled sample and A0 AIM samples all resolve under `advanced_inventory::display`; the call graph is dominated by SDL input waits / renderer synchronization, not an identified expensive item-processing function. The sample has 1531 main-thread observations during an AIM interval, but it is not an activity-only profile. A1 coarse CPU window at same prompt frame: 0.80 CPU s over 8.53 wall s (9.38% of one core), RSS 1.22 GB; this is between-observation UI time, not the transfer operation. A0 recorded 34.08 CPU s over 441.86 s (7.71% one core) across an activity-wait observation interval; also not transfer-only.

B0 zone-menu-idle sample (768 samples) shows time in `loot()` / `uilist::query` and input waiting before selection; it is not a sample of `zone_sort_activity_actor::stage_do`. Native per-turn traces yield similar B0/B1/B2 operation envelopes but do not sample CPU stacks inside sorting. Existing evidence therefore separates UI waiting from game-turn progression qualitatively, but does not identify a costly transfer/sort function or a valid before/after CPU optimization. A future informative profile needs sampling or function timing during the actual AIM transfer stage and `zone_sort_activity_actor::stage_do`, with identical item counts and observation boundaries. The B2 save and current census/semantic trace remain retained for the follow-on conservation repair.
